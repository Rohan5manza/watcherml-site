WHY WATCHERML EXISTS

The crash is one line.
The cost is everything before it.

CUDA out-of-memory failures can erase hours or days of GPU training. The exception is obvious. Reconstructing why it happened, and proving which intervention fixes it, is not.

CUDA OOM HORROR STORIES
01 / 03
train_llm.py FAILED AFTER 71H 48M
step 48,996 / 50,000 running final validation... RuntimeError: CUDA out of memory. Tried to allocate 2.00 GiB. GPU 0 has 312 MiB free.
THE 99% EPOCH CRASH

Three days of training. One validation batch ends it.

The training loop fits, but validation uses a larger batch or longer sequence. VRAM crosses its limit near the finish and the entire run terminates.

  • Failure appears only in a later training phase
  • The last successful state may not explain the spike
  • Rerunning the full job to test one change is expensive
finetune.py OOM WITH BATCH SIZE 1
model = "llm-7b" batch_size = 1 max_length = 4096 gradient_checkpointing = true torch.cuda.OutOfMemoryError
THE LONG-CONTEXT TRAP

Even the smaller model still runs out of memory.

Batch size is already one. Mixed precision and gradient checkpointing are enabled. But sequence length, activations, optimizer state, and temporary allocations still exceed VRAM.

  • Several memory variables interact at once
  • The obvious intervention may already be exhausted
  • A successful launch does not guarantee stable headroom
recovery_notes.txt ATTEMPT 07
✓ lowered batch size ✓ enabled mixed precision ✓ shortened sequences ✓ emptied CUDA cache Result: CUDA OOM still reproduced
CONFIGURATION ROULETTE

Change a setting. Pay for another run. Commit risky yolo runs.

Without a preserved failure record and a controlled recovery contract, engineers test loosely related fixes without knowing whether the original failure was reproduced or truly resolved.

  • Trials are difficult to compare reliably
  • Multiple changes obscure which intervention mattered
  • A completed probe can be mistaken for a verified recovery

02 CHANGE THE GPU ECONOMICS

Reject obvious failures before paying for another complete job.

If a full attempt takes eight GPU-hours, three manual retries can consume up to 24 GPU-hours. WatcherML evaluates candidates with bounded probes before promoting a survivor.

A probe cannot guarantee that a late-stage OOM is gone—but it can cheaply eliminate candidates that fail immediately.

04 TRUST THE COMPARISON

Every trial starts in a fresh process—not a haunted notebook.

Notebook reruns can inherit cached CUDA allocations, old model objects, modified globals, optimizer state, imported modules, and partially executed cells.

WatcherML rebuilds each candidate in an isolated worker and releases the child CUDA context when the worker exits.

NEAREST-SUCCESS DIFF

Compare with a relevant success—not merely the latest run.

Use model/configuration, dataset fingerprint, hardware, Git state, framework environment, and recency to select a stronger baseline and expose failure-relevant differences.

◇
BOUNDED INTERVENTION POLICY

Propose one explainable OOM intervention at a time.

Choose only from an explicit allowlist such as batch size, gradient accumulation, or gradient checkpointing. Each proposal records its evidence, rationale, and expected effect.

↻
FRESH-PROCESS TRIALS

Test recovery without contaminating the source run.

Launch every variant in a new process with a declared entrypoint and serialized configuration. Capture its exit code, timeout, metrics, resources, and failure capsule independently.

✓
CONTRACT VERIFICATION

Prove more than “the process did not crash.”

Require the trial to avoid OOM, reach a minimum step, respect memory and metric-regression limits, and survive confirmation runs before WatcherML calls it recovered.

⎇
RECOVERY RECORD

Remember only interventions that passed verification.

Store the source capsule, proposed patch, isolated-trial outcome, verifier results, and confirmation evidence as an auditable campaign—not as an opaque “best run.”

DEFINE RECOVERY BEFORE RUNNING TRIALS

Every campaign begins with a strict contract.

WatcherML does not search for a better hyperparameter score. It tests whether a bounded intervention resolves the captured OOM while preserving declared training behavior.

  • Explicit training entrypoint and source configuration
  • Allowlisted, config-only interventions for v1
  • Maximum trials, timeout, and wall-clock budget
  • Minimum progress, metric-regression limit, and confirmation runs
  • Fresh process and complete evidence for every attempted trial
oom-recovery.yaml● explicit
source:
  run_id: mistral-lora-7f21
  failure_class: cuda_out_of_memory

entrypoint:
  callable: train:main
  config: config.json

verify:
  min_steps: 500
  confirmation_runs: 2
  metric: validation_loss
  max_regression: 0.01

budget:
  max_trials: 6
  trial_timeout_minutes: 30
  max_wall_minutes: 90

allow:
  config_keys:
    - batch_size
    - gradient_accumulation_steps
    - gradient_checkpointing

CONTROLLED BY CONSTRUCTION

A recovery trial is evidence, not a guess.

WatcherML v1 cannot rewrite training code, install dependencies, alter datasets, or silently keep searching. It applies an allowed configuration patch in a fresh process and records exactly what happened.
